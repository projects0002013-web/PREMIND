# Подключение аккаунтов и базы PREMIND

Облачная часть необязательна. Без настройки сайт работает локально. Для реальных входов нужен ваш проект Supabase; создать проект, применить SQL и подключить Google должен владелец аккаунтов. Эти действия не были выполнены автоматически.

## 1. Создать базу

1. Создайте проект на https://supabase.com/dashboard, выберите подходящий регион хранения данных.
2. В SQL Editor выполните **один раз** файл `supabase/migrations/202610150001_accounts.sql`. Альтернатива для настроенного CLI: `supabase link`, затем `supabase db push`.
3. Таблица `research_backups` хранит одну полную копию базы на аккаунт. Учётные записи, пароли и email обслуживает Supabase Auth; пароли приложение не хранит самостоятельно.
4. RLS запрещает анонимный доступ и разрешает пользователям читать/изменять только строку со своим `auth.uid()`. Не отключайте RLS. Публичный ключ не даёт доступа к чужим исследованиям.

## 2. Настроить адреса возврата

Supabase → Authentication → URL Configuration:

- Site URL: `https://projects0002013-web.github.io/PREMIND/`
- Redirect URLs: `https://projects0002013-web.github.io/PREMIND/`
- Для разработки отдельно разрешите `http://localhost:5173/PREMIND/`.

Точные адреса должны совпадать с размещением сайта, включая путь и завершающий `/`. HashRouter не используется для OAuth callback: вход возвращает код PKCE в query корневой страницы, SDK обменивает его на сессию. Если проверяете в другом браузере/на другом устройстве ссылку подтверждения или сброса, PKCE verifier может отсутствовать; повторите запрос в том браузере, где будете открывать письмо.

## 3. Включить Google

1. Google Cloud Console → APIs & Services → OAuth consent screen: настройте приложение и разрешённые домены. Для режима Testing добавьте тестовых пользователей; для публичного доступа завершите требования Google к публикации OAuth-приложения.
2. Credentials → Create OAuth client ID → Web application.
3. В Authorized redirect URIs добавьте **Supabase callback** из настроек провайдера: `https://<project-ref>.supabase.co/auth/v1/callback`. Это адрес Supabase, а не GitHub Pages.
4. Supabase → Authentication → Sign In / Providers → Google: включите провайдера, вставьте Client ID и Client Secret Google.
5. **Google Client Secret храните только в Supabase.** Не добавляйте его в Vite, репозиторий или чат. PREMIND не запрашивает доступ к Google Drive, Gmail или контактам.

Для email включите Email provider и подтверждение адреса. Для публичного приложения настройте свой SMTP и квоты отправки в Supabase; встроенная почта имеет ограничения. Политику паролей, rate limits и защиту от злоупотреблений задаёт Supabase Auth. Форма регистрации требует не менее 8 символов.

## 4. Подключить сайт

В Project Settings → API / Connect найдите Project URL и **publishable key** (`sb_publishable_...`). Допускается legacy `anon` JWT через `VITE_SUPABASE_ANON_KEY`, но новый публичный ключ предпочтителен.

Локально скопируйте `.env.example` в `.env.local` и укажите:

```dotenv
VITE_SUPABASE_URL=https://<project-ref>.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
```

Перезапустите Vite. Для Pages: GitHub → Settings → Secrets and variables → Actions → **Variables**, добавьте переменные с этими двумя именами. Запустите workflow заново: настройки Vite встраиваются при сборке. Изменение переменных без пересборки не меняет опубликованный сайт.

Publishable/anon ключ публичный и виден в браузере. **Никогда не используйте service_role, sb_secret_, Google Client Secret или пароль базы в VITE_*:** они дают повышенный доступ и не предназначены для фронтенда. Приложение отклоняет серверные ключи в конфигурации.

Если сеть облачной среды ограничена, разрешите HTTPS до `<project-ref>.supabase.co` (или вашего собственного Supabase-домена). Для авторизации в браузере также требуется доступ к Google. Приложение не проксирует OAuth через Codex.

## 5. Как пользоваться

1. Нажмите «Войти» в правом верхнем углу или «Открыть аккаунт» в настройках.
2. Выберите Google либо регистрацию по email. Подтвердите email при необходимости. Восстановление пароля выполняется по письму и показывает форму нового пароля после возврата.
3. Войдя, нажмите «Проверить облачную копию». Вход сам по себе не отправляет результаты.
4. Отметьте отдельное согласие на загрузку исследовательских данных и нажмите «Сохранить в облако», затем подтвердите.
5. На другом устройстве войдите в тот же аккаунт, проверьте копию и выберите «Загрузить на устройство». Текущая локальная база сначала скачивается в JSON, затем заменяется. Автоматического объединения и фоновой синхронизации нет.
6. «Удалить облачную копию» требует подтверждения и не удаляет локальные данные. «Удалить все данные» в настройках очищает только это устройство. Для удаления Auth-аккаунта владелец проекта использует Supabase Authentication → Users; внешним ключом облачная копия удалится вместе с аккаунтом.

Смена аккаунта и выход не очищают локальную базу. На общем устройстве очистите локальные данные перед передачей устройства. Не сохраняйте данные одного участника в аккаунт другого человека без разрешения. Подтверждение облачного согласия сбрасывается при смене аккаунта.

## Устройство и ограничения

Сохраняются весь документ схемы v1, результаты, самооценки и комментарии, эксперименты, участники и отметки согласия. Максимум 20 MiB (проверка клиента и БД). JSONB хранится с дополнительными пробелами, поэтому сервер может отклонить документ, близкий к лимиту. Не размещайте реальные имена в комментариях. Согласие на локальное исследование не заменяет согласие на передачу данных стороннему облачному провайдеру; для несовершеннолетних нужны разрешения представителей и школы. Владелец проекта определяет правила обработки, регион, срок хранения и запросы на удаление.

Обновление и удаление используют сравнение ревизии (optimistic concurrency). Если другое устройство уже изменило копию, операция отклоняется; обновите сведения, экспортируйте локальную копию, затем явно выберите нужную версию. Автоматического last-write-wins нет. Часы/ревизии назначает БД, не клиент. Сессии Auth сохраняются SDK в браузере; на общих устройствах выходите из аккаунта. Service worker кэширует только статические файлы этого сайта, не ответы Supabase или токены.

## Проверка после подключения

- Google login возвращает на правильный Pages URL.
- Регистрация с подтверждением почты, вход и восстановление пароля работают с вашим SMTP.
- Два тестовых аккаунта не видят и не изменяют копии друг друга, в том числе прямыми REST-запросами (RLS).
- Загрузка без согласия невозможна в интерфейсе; вход не отправляет результаты.
- Создайте копию на одном устройстве, загрузите на другом, проверьте результаты и протокол.
- Откройте две вкладки, получите одну ревизию: сохранение из первой должно сделать сохранение из второй конфликтным.
- Удаление облачной копии оставляет локальную базу; выход и офлайн-режим не мешают локальным тестам.

Локальные unit/интеграционные проверки SDK-контрактов и интерфейса не заменяют эти проверки на настоящем проекте Supabase и Google OAuth.
